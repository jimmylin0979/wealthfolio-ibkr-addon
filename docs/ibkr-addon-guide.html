A. 概述

這個附加元件把 Interactive Brokers（IBKR）的活動報表（Activity Statement）匯入 Wealthfolio， 並自動處理多幣別情境。它有兩條資料來源路徑：

  • CSV 手動上傳：一次上傳多份 IBKR 活動報表 CSV（最多 MAX_FILES = 20 個檔案，單檔上限 50MB）。
  • Flex Query API 自動抓取：透過 IBKR Flex Web Service 兩階段 HTTP API 取得報表 CSV，可設定在投資組合更新後自動同步。

匯入管線會做這些事：

  1. 解析 IBKR 多區段 CSV（Trades、Cash Transactions、Transfers 等區段合併）。
  2. 偵測所有出現的幣別，為每個幣別建立（或重用）一個 Wealthfolio 帳戶，命名規則 {group} - {ccy}。
  3. 用 ISIN 或 symbol 透過 ctx.api.market.searchTicker 解析成 Yahoo Finance 相容 ticker。
  4. 把 IDEALFX 外匯轉換拆成 TRANSFER_OUT / TRANSFER_IN 成對交易。
  5. 用交易指紋（fingerprint，金額正規化到 toFixed(6)）去重，避免 CSV 與 Flex Query 重複匯入。
  6. 呼叫 ctx.api.activities.import 寫入，並回報每個帳戶的成功／失敗筆數。

主機需求與載入方式

元件是純 TypeScript / React 19 專案，經 Vite lib mode 打包成單一 ES bundle dist/addon.js， 由 Wealthfolio 主機依 manifest.json 載入。重點約束：

  • 主機版本必須 ≥ 3.6.2（minWealthfolioVersion，安裝與啟用時硬性檢查）。
  • sdkVersion 為 3.9.0（主機只做警告，不阻擋）。
  • SDK 3.9 已移除 ctx.api.http，Flex 請求改走主機代理的 ctx.api.network.request（僅限 HTTPS，且目的地必須在 manifest 的 network.allowedHosts，本元件只允許 ndcdyn.interactivebrokers.com）。
  • 主機 ≥ 3.6.0 要求路由與側邊欄項目掛在 /addon/<ns> 或 /addons/<ns> 命名空間下（ns 即 addon id）。

B. 匯入嚮導逐步流程（5 個步驟）

嚮導頁面是 src/pages/ibkr-multi-import-page.tsx。畫面頂部的步驟指示器顯示 4 個標籤 （Source & Group、Currency Accounts、Transaction Preview、Import Results）， 其中 ticker 解析與交易預覽在同一個 UI 步驟內先後執行。本手冊依邏輯拆成 5 個步驟說明。

Step 1來源選擇（Source & Group）

使用者操作
輸入帳戶群組名稱（例如 TFSA、Trading，會成為帳戶名稱與 group 欄位的前綴）， 選擇資料來源：Import from CSV Files（上傳檔案）或 Flex Query （輸入 Token 與 Query ID，可勾選 remember credentials）。
呼叫的 API
  • Flex 路徑：fetchFlexQuery({ token, queryId })（src/lib/flex-query-fetcher.ts）， 底層走 IBKR Flex Web Service 兩階段 API（詳見 C 節）， 傳輸層為 ctx.api.network.request。成功後若勾選記住憑證，先經 validateFlexToken（16 到 128 位英數字）與 validateQueryId（純數字，≤ 20 碼）驗證， 再寫入 ctx.api.secrets.set("flex_token", ...) 與 ctx.api.secrets.set("flex_query_id", ...)。 取得的 CSV 交給 parseFlexQueryCSV（內部重用 extractTradesSection，與手動 CSV 走完全相同的轉換路徑）。
  • CSV 路徑：useMultiCsvParser.parseMultipleCsvFiles(files)（src/hooks/use-multi-csv-parser.ts）。 先驗證：檔案數 ≤ 20、單檔 ≤ 50MB、副檔名 .csv、讀檔 30 秒逾時。 再用 extractTradesSection（src/lib/ibkr-csv-splitter.ts）把 IBKR 多區段 CSV （同一檔內串接的 Trades、Dividends、Transfers 等區段）合併成列陣列，並正規化欄位名稱。
  • 頁面載入時也會呼叫 ctx.api.accounts.getAll()（取得既有群組清單）與 ctx.api.secrets.get（讀回先前儲存的 Token / Query ID）。
預期結果
解析成功：得到 CsvRowData[] 列陣列，自動進入 Step 2。 解析失敗：畫面顯示可見錯誤（藍色訊息列顯示載入進度或 Error: ...，琥珀色框顯示逐檔解析錯誤）。 結構性失敗會直接 throw，例如 No trades section found 或 No valid IBKR sections found。

Step 2幣別帳戶預覽（Currency Accounts）

使用者操作
檢視偵測到的幣別與各幣別交易筆數，必要時修改帳戶名稱。名稱重複、名稱空白、或與既有帳戶幣別不符時無法繼續。
呼叫的 API（皆為內部 lib 函式）
  • detectCurrenciesFromIBKR(parsedData)（src/lib/currency-detector.ts），兩層偵測：
    1. 主路徑：只讀完整活動報表 Cash Report 中 LevelOfDetail === "Currency" 的彙總列，取其 CurrencyPrimary。
    2. Fallback（Flex Query CSV 永遠沒有 Cash Report 區段，一定走這條）：從交易列推導， 來源有三個：ListingExchange 經 EXCHANGE_TO_CURRENCY 對應表映射的幣別（trades 與 TTAX/OFEE 稅費列）、 IDEALFX 列的 Symbol 幣別對（例如 HKD.USD 拆出 HKD 與 USD，只套用於 IDEALFX，不會誤拆 BRK.B 這類一般點號 symbol）、 以及符合大寫 ISO-3 格式的 CurrencyPrimary。
  • generateAccountNames(groupName, currencies)：產生 {group} - {ccy} 預設帳戶名。
  • countTransactionsByCurrency(parsedData)：統計各幣別交易筆數（優先 ListingExchange 對應幣別，否則 CurrencyPrimary）。
  • 與 Step 1 載入的既有帳戶比對（name + currency 都相符才算既有帳戶，將被重用）。
預期結果
每個幣別一列可編輯的帳戶預覽（幣別、交易筆數、帳戶名稱、狀態 New/Existing）。 頁面文案為 Detected N currencies across all files。 偵測到 0 個幣別時 canProceed 為 false，下一步按鈕被阻擋，這就是「Detected 0 currency」錯誤狀態。

Troubleshooting：「Detected 0 currency」

可能原因與對症方法：

  • Flex CSV 沒有 Cash Report 區段：這是 Flex Query 的常態，fallback 機制就是為此而設。若 fallback 也抓不到，代表交易列缺少 ListingExchange、CurrencyPrimary，且沒有 IDEALFX 列。檢查 Flex Query 欄位設定（見 C 節），確認有勾選 ListingExchange 與 CurrencyPrimary。
  • Token 或 Query ID 錯誤：這種情況通常不會走到 Step 2，IBKR 會先回錯誤碼（1015 token 無效、1012 token 過期、1014 query 無效），錯誤訊息會顯示在 Step 1。
  • CSV 檔沒有 Trades 區段：extractTradesSection 會直接 throw（No trades section found），同樣停在 Step 1。
  • 檔案開頭有 BOM：區段偵測靠 line.startsWith('"ClientAccountID"') 比對表頭，BOM 字元會讓它失效。用「UTF-8 無 BOM」重新存檔。

Step 3Ticker 解析（在 Transaction Preview 步驟內執行）

使用者操作
在 Step 2 按下一步後等待，畫面顯示解析進度（current / total）。不需要輸入。
呼叫的 API
  • refreshAndUpdateAccountPreviews：先呼叫 ctx.api.accounts.getAll() 重新整理帳戶，更新預覽的 existingAccount。
  • processAndResolveData(parsedData, previews, ctx.api.market.searchTicker, onProgress)（src/lib/import-orchestrator.ts），內部依序：
    1. preprocessIBKRData：列分類，標記 _IBKR_TYPE。
    2. resolveTickersFromIBKR（src/lib/ticker-resolution-service.ts + ticker-resolver.ts）： 以 ISIN 或 symbol 查詢 ctx.api.market.searchTicker，批次間隔 TICKER_RESOLUTION_DELAY_MS = 50ms 避免 rate limit； 結果快取在 localStorage，上限 TICKER_CACHE_MAX_ENTRIES = 1000 筆，單筆最長保存 30 天。
    3. convertToActivityImports：把列轉成 ActivityImport，回傳轉換錯誤清單（ConversionError[]，浮現而非靜默吞掉）。
    4. splitFXConversions：拆外匯轉換（見 Step 4）。
預期結果
已解析 ticker 的交易清單；解析失敗的項目與轉換錯誤（例如缺日期的列）會顯示為警告，例如 N transaction(s) failed to convert、N FX conversion(s) skipped。 若 processAndResolveData 整體 throw，流程停在這裡（fatal）。

Step 4交易預覽（Transaction Preview）

使用者操作
檢視依幣別帳戶分組的交易預覽與各組摘要，確認後按 Start Import。
呼叫的 API
  • splitFXConversions（src/lib/fx-transaction-splitter.ts）：把 IDEALFX 外匯交易拆成 TRANSFER_OUT（來源幣別帳戶）+ TRANSFER_IN（目標幣別帳戶）成對活動；缺帳戶或格式無效的轉換列入 SkippedFXConversion[] 警告。
  • fetchExistingActivitiesForDedup：對每個既有帳戶呼叫 ctx.api.activities.getAll(accountId)，取回現有活動。
  • deduplicateActivities（src/lib/activity-deduplicator.ts）：以指紋比對新舊活動， 指紋格式為 date|symbol|type|qty/amount 細節|fee|currency，數值一律 toFixed(6) 正規化， 所以 CSV 與 Flex Query 匯入同一筆交易也能正確判重。重複的直接剔除。
  • groupActivitiesByCurrency + createTransactionGroups：依幣別分組， 每組計算摘要（trades、dividends、deposits、withdrawals、fees、other）。沒有 currency 的活動會被跳過並記錄警告，不會靜默預設幣別。
預期結果
交易依幣別帳戶分組顯示，每組有類型摘要與筆數。去重後剩下的活動就是 Step 5 實際會匯入的內容。 部分帳戶讀取失敗時顯示警告（這些帳戶可能產生重複匯入）。

Step 5匯入（Import Results）

使用者操作
按 Start Import，等待進度（Creating account: ... / Importing N transactions to ...），完成後檢視結果，可按重置再跑一輪。
呼叫的 API
  • ctx.api.accounts.create({ name, currency, group, accountType: "SECURITIES", isDefault: false, isActive: true })： 為每個尚不存在的幣別帳戶建立帳戶；另外會掃描所有交易的實際幣別，預先補建缺少的幣別帳戶（避免匯入階段競態）。
  • ctx.api.activities.import(transactionsWithAccountId)：逐幣別群組匯入，每筆活動先填上目標帳戶的 accountId。 去重已在 Step 4 完成，這裡直接寫入。
  • ctx.api.activities.checkImport：在 manifest.json 中宣告（activities:checkImport 權限）， 供匯入前檢查使用；目前程式碼的匯入路徑直接呼叫 activities.import，判重由 addon 內部指紋機制負責。
預期結果
每個帳戶一列結果：success（成功筆數）、failed（失敗筆數）、errors（逐筆錯誤訊息， 例如某幣別沒有可用帳戶、或 import 呼叫失敗）。部分成功也會如實呈現。 完成後可到 Wealthfolio 的 Accounts / Activities 頁面驗證。

C. Flex Query API 細節

實作在 src/lib/flex-query-fetcher.ts。IBKR Flex Web Service 是兩階段 HTTP API（v=3）， Base URL 為 https://ndcdyn.interactivebrokers.com/AccountManagement/FlexWebService。

兩階段交換流程

Addon                          IBKR Flex Web Service
  |                                      |
  |  (1) GET /SendRequest                |
  |      ?t=TOKEN&q=QUERY_ID&v=3         |
  |------------------------------------->|
  |        XML: <Status>Success          |
  |        <ReferenceCode>xxx            |
  |        <Url>(optional)               |
  |<-------------------------------------|
  |                                      |
  |  (2) GET /GetStatement               |
  |      ?t=TOKEN&q=REFERENCE_CODE&v=3   |
  |------------------------------------->|
  |   ErrorCode 1003/1019 (生成中)        |
  |   --> 等 2s 再試, backoff x1.5        |
  |       上限 30s, 絕對逾時 2 分鐘        |
  |<-------------------------------------|
  |   ErrorCode 1018 (rate limit) --> 同上重試
  |   其他 ErrorCode --> 立即失敗 (fail fast)
  |                                      |
  |   成功: 回應本體即為 CSV              |
  |      (格式依 Flex Query 設定)         |
  |<-------------------------------------|

階段一：SendRequest

GET https://ndcdyn.interactivebrokers.com/AccountManagement/FlexWebService/SendRequest?t=TOKEN&q=QUERY_ID&v=3

回應是 XML，parseFlexResponse 會抽出 <Status>、<ReferenceCode>、 <Url>、<ErrorCode>、<ErrorMessage>。 Status === "Success" 且有 ReferenceCode 才算成功。 XML 字串會經 sanitizeXmlString 清除標籤與限制長度；<Url> 只有在是 HTTPS 且位於 *.interactivebrokers.com 或 *.ibkr.com 時才接受。

階段二：GetStatement（輪詢）

GET https://ndcdyn.interactivebrokers.com/AccountManagement/FlexWebService/GetStatement?t=TOKEN&q=REFERENCE_CODE&v=3

fetchFlexQuery 的輪詢參數（預設值來自 src/lib/constants.ts）：

  • 可重試錯誤碼：1003、1019（報表生成中）與 1018（rate limit）。
  • 其他錯誤碼一律 fail fast，不重試。
  • 初始延遲 FLEX_QUERY_INITIAL_DELAY_MS = 2000（2 秒），每次乘 1.5，上限 FLEX_QUERY_MAX_DELAY_MS = 30000（30 秒）。
  • 最多重試 maxRetries = 10 次，另有絕對逾時 FLEX_QUERY_ABSOLUTE_TIMEOUT_MS = 120000（2 分鐘）防止無限等待。
  • 成功時回應本體就是 CSV 字串（因為 Flex Query 的 Format 設為 CSV）。

傳輸層與安全注意事項

安全：token 在 URL 裡

IBKR 的 API 設計就是把 token 放在 URL query 參數 ?t=TOKEN（不是 Authorization header）。 因此絕對不要記錄完整請求 URL，token 會直接出現在 log 裡。addon 內部只 log 進度訊息與 ReferenceCode。

  • 所有請求經主機代理：createNetworkHttpClient(ctx.api.network)（src/lib/network-http-client.ts）把 SDK 3.9 的 network.request({ url, method, headers, body, timeoutSecs }) 包裝成 fetcher 的 HttpClient 介面。
  • 只允許 HTTPS，且目的地必須在 manifest network.allowedHosts：["ndcdyn.interactivebrokers.com"]。安裝時使用者需同意 network 權限，實際請求才會放行。
  • 逾時：預設 timeoutSecs = 60（IBKR 生成報表可能超過 10 秒），主機上限 120 秒。
  • 請求帶 User-Agent: Wealthfolio/1.0。
  • Token 驗證規則：16 到 128 位、僅英數字（MIN_TOKEN_LENGTH / MAX_TOKEN_LENGTH）。Query ID：純數字、最長 20 碼。

D. Auto-fetch（自動同步）

啟用 auto-fetch 的 Flex Query 設定會在投資組合更新完成後自動抓資料並匯入，全程無需開嚮導。 整條鏈路在 src/addon.tsx（performAutoFetch）與 src/lib/auto-fetch-processor.ts（processFlexQueryConfig）。

觸發與併發保護

  1. 事件：ctx.api.events.portfolio.onUpdateComplete(debouncedAutoFetch)。註冊採 fire-and-forget，失敗只記 warning，不影響 addon 其他功能。
  2. Debounce：AUTO_FETCH_DEBOUNCE_MS = 5000。5 秒內的多個更新事件合併成一次抓取。
  3. AsyncLock：autoFetchLock.tryAcquire() 非阻塞取鎖，已有抓取進行中就直接跳過。
  4. Token 檢查：loadToken(ctx.api.secrets)（key flex_token），沒有 token 就跳過。
  5. 設定載入：loadConfigsSafe(ctx.api.secrets)（key flex_query_configs，JSON 陣列），篩出 autoFetchEnabled === true 的設定。讀取失敗會 log error（不會跟「沒有設定」混淆）。
  6. Per-config cooldown：isConfigInCooldown(config.lastFetchTime)，冷卻時間 FETCH_COOLDOWN_MS = 6 小時（IBKR 活動報表每日更新一次，6 小時已足夠）。冷卻中則跳過該設定。
  7. TOCTOU 再檢查：真正抓取前重新 loadConfigsSafe 讀最新設定、重跑 cooldown 檢查，然後用 updateConfigStatus(secrets, id, createPendingStatus()) 先「認領」這個設定（寫入 lastFetchTime），避免多個觸發來源重複抓同一個設定。認領失敗就跳過。

單一設定的處理流程（processFlexQueryConfig）

  1. fetchAndParseFlexQuery：fetchFlexQuery（兩階段 API，同 C 節）取得 CSV，parseFlexQueryCSV 解析成列。0 列時直接記成功狀態並顯示「No new transactions found」。
  2. detectCurrenciesFromIBKR(rows) 偵測幣別（同 Step 2 的兩層邏輯）。
  3. getOrCreateAccountsForGroup(accountGroup, currencies)：ctx.api.accounts.getAll() 找同名同幣別帳戶，缺的用 ctx.api.accounts.create（SECURITIES 型別）補建。
  4. processAndResolveData(rows, previews, ctx.api.market.searchTicker)：preprocess、ticker 解析、轉換、FX 拆分（與嚮導共用同一條管線）。轉換錯誤寫入 warning log（前 5 則摘要）。
  5. importActivitiesToAccounts：逐幣別帳戶，先用 createActivityFingerprintGetter(activitiesApi) 取回該帳戶既有活動指紋， deduplicateActivities 剔除重複，剩下的呼叫 ctx.api.activities.import。統計 imported / skipped / failed 與失敗帳戶清單。
  6. updateConfigStatus(ctx.api.secrets, config.id, createSuccessStatus())：把最後抓取時間與狀態寫回 secrets（flex-config-storage.ts，所有寫入都經 loadConfigsOrThrow + withLock，讀取錯誤會 throw 而不是回傳空陣列，避免把既有設定整組洗掉）。

預期結果

  • 成功：toast（透過主機注入的 window.__wealthfolio_toast__，sonner 介面）顯示 IBKR: {config name}， 描述為 formatImportResultMessage(imported, skipped, failed) 的匯入／跳過／失敗筆數。有失敗帳戶時改用 warning toast。
  • 失敗：error toast，訊息經 enrichIBKRErrorMessage 加上可操作指引（例如 token 無效該去哪裡重產生）； 錯誤狀態經 createErrorStatus 存回設定（lastFetchError），設定頁可看到。
  • 整個過程的詳細進度寫入 ctx.api.logger（trace / info / warn / error）。

F. 故障排除

1. 「Detected 0 currency across all files」（Step 2 被阻擋）

原因與修法

  • Trades 區段缺 TransactionType / Exchange（實測最常見）：README 的必要欄位清單沒有列這兩欄，照著設定就會讓區段無法被辨識為 Trades，extractTradesSection 拋出 No trades section found in IBKR CSV，解析結果為 0 列。修正版已改用 Buy/Sell 單獨判定並容忍缺少 transaction type，但仍建議在查詢中勾選 TransactionType、Exchange、ListingExchange（見 README 的 TODO）。
  • Flex CSV 沒有 Cash Report：Flex Query CSV 本來就不含 LevelOfDetail="Currency" 彙總列，主路徑抓不到是預期行為，fallback 會從交易列推導幣別。若 fallback 也是 0，代表交易列同時缺少 ListingExchange、有效的 CurrencyPrimary（大寫 ISO-3），且沒有 IDEALFX 列。
  • Token / Query ID 錯誤：會在 Step 1 就以 IBKR 錯誤碼失敗（1015 token 無效、1012 token 過期、1014 query 無效、1020 token 或請求無效），不會走到幣別偵測。用 IBKR Settings 頁的 Test 按鈕驗證。
  • 格式不是 CSV：若 Flex Query 的 Delivery 格式設成 XML，回應無法當 CSV 解析，解析錯誤會直接顯示在載入訊息中。
  • BOM：見下方第 4 項。

1b. 「0 transactions ready to import」（Step 3 预览為 0）

原因與修法

  • 日期欄位取錯（實測根因）：Flex CSV 完全沒有 Date 與 ReportDate 欄位，Trades 用 TradeDate、Cash Transactions 用 Date/Time（值如 2026-06-30 202000）。若轉換時只讀 row.Date || row.ReportDate，每一列都會被判定為「Missing date field」而丟棄，預覽就會是 0 筆。轉換前必須 fallback 到 TradeDate，並把 Date/Time 尾端的時間剝掉，否則匯入主機時日期格式不合法。
  • 全部被判定為重複：若先前已匯入過相同交易，指紋去重會全部略過。確認目標帳戶是否已有相同活動。

1c. 匯入後金額或筆數異常

Statement of Funds 重複計算

Flex 回應的第 1 個區段是 Statement of Funds，內容是 trades / dividends / deposits 的現金基礎彙總， 與其他區段的交易列重複。完整 Activity Statement 會在這些列標上 LevelOfDetail 讓預處理器略過， 但 Flex 的 Statement of Funds 沒有這個欄位，因此修正版在區段分割階段就整段丟棄（辨識特徵： ActivityCode + ActivityDescription + Debit/Credit）。 實測未排除時 6 筆股息會變成 12 筆。

1d. 「Add-on permission denied ... tried to use 'X' without permission」

原因與修法

主機的 sandbox 會逐一比對 manifest 宣告的權限，任何未宣告的 ctx.api.* 呼叫都會被攔截並彈出這個 toast。 允許清單由 permissions[].functions[].name 組成，比對時用 category:name（ui、logger、 query、toast 為 baseline，不需宣告）。

  • namespace 名稱不等於 category 名稱：ctx.api.market.searchTicker 的 category 是 market-data； ctx.api.events.portfolio.onUpdateComplete 的 category 是 events（function 為 onUpdateComplete）。 照 namespace 名寫會被判定為未宣告。
  • 本 addon 需要的 activities 權限是 getAll 與 import：getAll 供指紋去重讀取既有活動 （import-orchestrator.ts、auto-fetch-helpers.ts），漏掉會讓去重步驟直接失敗。
  • 修改 manifest 後：dev 模式需重載 addon（主機每次載入都會重新註冊 manifest）；以 ZIP 安裝則需重新安裝／更新。
  • 在哪裡看權限：設定 → Addons → 該 addon 卡片上的「眼睛」圖示。注意它在桌面寬度下預設為透明 （sm:opacity-0 group-hover:opacity-100），必須把滑鼠移過卡片才會顯示。

2. 開發模式：側邊欄空白或主機 404

Wealthfolio 3.7+ 的 addon 開發協定要求 dev server 提供 /runtime-package、帶 generation 的 /status、 以及 /addon-updates SSE 端點，缺了主機直接 404。請用 pnpm dev:full （vite watch build + dev-server.mjs 在 port 3001，已實作完整協定），不要只用 pnpm dev。 另外，路由若沒掛在 /addons/ibkr-multi-import/* 命名空間下，enable() 會 throw，症狀就是側邊欄空白。

3. Token 跟 Query ID 搞混

這是兩個不同的東西：Flex Web Service Token 是整組 API 的共用憑證（英數字串，16 到 128 位，放在 ?t=）， 在 Reports > Flex Queries 頁面底部的 Flex Web Service 區塊產生； Query ID 是單一 Flex Query 的數字編號（放在 ?q=），顯示在查詢名稱旁邊。 打錯 token 得到 1015（或過期的 1012），打錯 Query ID 得到 1014。

4. BOM 讓區段偵測失效

ibkr-csv-splitter.ts 靠 line.startsWith('"ClientAccountID"') 比對表頭來偵測區段， 檔案開頭的 UTF-8 BOM 字元會讓第一行比對失敗（已知限制）。把 CSV 重存為「UTF-8（無 BOM）」即可。

5. Transfers 被靜默跳過

README 的 Transfers 必要欄位清單漏了 TransferCompany 與 CashTransfer，但解析器需要這兩個表頭； 缺少時 transfer 列會被分類為 unknown 並直接丟棄，沒有任何錯誤訊息。請在 Flex Query 的 Transfers 區段把這兩個欄位也勾選。
